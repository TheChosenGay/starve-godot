# 客户端性能排查手册

> 本文记录"客户端卡顿"的排查路径与实测基线。**先按本文的顺序排除环境因素，
> 再怀疑代码**——我们曾花了很多轮去优化着色器和 GC，最后发现根因是
> **显示器被设成了 30Hz**。

## 0. 排查顺序（重要）

按以下顺序，**从外到内**。前面的没排除掉，后面的结论都可能是噪声。

| 顺序 | 检查项 | 怎么查 | 典型症状 |
| --- | --- | --- | --- |
| 1 | **显示器刷新率** | 系统设置 → 显示器 → 刷新率 | 帧率精确锁在刷新率或其 1/2 |
| 2 | 窗口是否在前台 | 点一下游戏窗口 | 后台窗口被 macOS 节流 |
| 3 | 其他进程抢资源 | `ps aux \| sort -rk3 \| head` | CPU 被打满 |
| 4 | 启动阶段 vs 稳态 | 看 F3 面板随时间变化 | 前 5~30 秒低、之后恢复 |
| 5 | GPU 子系统 | F3 面板的地形/云/植被开关 | 关掉某项明显提速 |
| 6 | 才轮到代码 | 本文下面的章节 | —— |

## 1. 显示器刷新率：最容易误判的一项（我们踩过）

### 症状特征

```
FPS 精确 = 30（或 60 / 120，即刷新率或其整数分之一）
frameMs 精确 = 33.33（= 1000/30，不是 33.5 或 34）
processMs ≈ frameMs   ← 但下面这条是关键
CPU 只有 3%
```

**`processMs` 很高但 CPU 很低 → 在等显示器，不是在算。**

### 怎么确认

```bash
system_profiler SPDisplaysDataType | grep -E "Resolution|UI Looks like|Main Display"
```

输出会形如：

```
HP D27k:
  Resolution: 3840 x 2160 (4K)
  UI Looks like: 1920 x 1080 @ 30.00Hz     ← 就是这里
  Main Display: Yes
```

### 注意

- **`--disable-vsync` 通常无效**：macOS 全屏下 Metal 仍按显示器刷新率提交。
  所以"关了 vsync 还是 30"**不能**排除刷新率问题（我们一度据此误判）。
- 4K 分辨率跑 30Hz 常见于**带宽不足**：HDMI 1.4 / 劣质线 / Type-C 转 HDMI
  转接头。换 **DisplayPort** 或降分辨率通常可恢复 60Hz。
- 多显示器时窗口在哪个屏，受哪个屏的刷新率约束。

## 2. 启动阶段：自定义着色器编译

### 症状

启动后前 **5~30 秒**帧率被锁在 30，之后自动恢复。期间 Godot 进程 CPU 打满。

### 原因

**Godot 的自定义着色器不进磁盘缓存。** 检查缓存目录会发现里面
全是引擎内置管线：

```bash
ls ~/Library/Application\ Support/Godot/app_userdata/<项目名>/shader_cache/
# SceneForwardClusteredShaderRD / SSAO / TAA / Fsr ... 唯独没有 res:// 下的 .gdshader
```

所以每次启动都要从源码重新编译我们那 8 个着色器。

### 已做的缓解

`GameRoot.WarmUpShaders()` 在启动时把着色器挂到离屏节点上强制编译，
把这段卡顿**前移到进入游戏之前**。实测 30FPS 期从 5~28 秒缩短到 3~4 秒。

注：这是**把卡顿前移，不是消除**——编译总量不变，且仍有 3~4 秒残留
（那部分是纹理/资源加载）。彻底消除需要预编译管线缓存，Godot 当前不提供。

## 3. 帧节拍（frame pacing）：平均 FPS 会骗人

**平均帧率正常不代表不卡。** 帧时间忽长忽短在视觉上就是"一顿一顿的"。

F3 面板的"帧节拍"行、以及日志里的 `frameMedianMs` / `frameP95Ms` /
`frameWorstMs` / `frameSpikeRatio` 专用于此。

实现见 `Starve.Core/FrameTimeStats.cs`（纯逻辑，可单测）。

> **坑**：`JitterRatio` 用**最坏帧**/中位数，不能用 P99/中位数。
> 偶发单帧尖峰（121 帧里 1 帧）在 P99 上取不到，比值会是 1、看不出问题。

## 4. 渲染子系统：A/B 隔离

F3 面板有地形/体积云/植被/Glow 开关，可逐个关闭做 A/B。

实测（Apple M4 Pro，1280×720，同一场景连续测量）：

| 配置 | FPS | 图元 |
| --- | --- | --- |
| 关地形 | 80 | 345,968 |
| 关云 | 80 | 618,564 |
| **全开** | **71** | 629,062 |

→ 地形与云**各占约 9 FPS（合计约 12%）**。

### 已做的着色器优化

1. **`fract(sin(n)*k)` → 整数 hash**：云/地形的噪声每像素调用上千次，
   `sin` 是 GPU 上的多周期超越函数。
2. **云影只算一次**：`cloud_shade()` 原先在 `fragment()` 与 `light()` 里
   各调一次、算的是同一个值。
3. **地面云影竖直采样 4 → 2 步**：云影的可见信息是**横向**漂移，
   纵向 4 个采样高度相关，属过采样。

> ⚠️ 注意：**地形着色器内联了自己的一份云噪声**，与场景里的
> `CloudLayer3D` 是两套独立开销。所以"关掉体积云，地形仍然很贵"是正常的。

## 4.5 体积云与地形云影：完整性能档案

> 这一节把体积云相关的**全部性能细节**集中记录，方便日后整理/迁移。
> 所有数字都经代码核实（括号内标注了对应的常量名与文件）。

### 4.5.1 成本模型（先理解这个，才能判断优化方向）

从最底层的 `hash()` 往上叠：

| 单元 | 成本 | 说明 |
| --- | --- | --- |
| `hash(float n)` | 1 次 `sin`（原）／7 次整数运算（现） | 见 4.5.3 |
| `noise(vec3)` | **8 次 hash** | 三线性插值的 8 个角点 |
| `fbm_clouds()` | **5 阶 noise = 40 hash** | `for (int i = 0; i < 5; i++)` |
| `density_func()` | **40 hash** | 1 次 fbm + 边界衰减 |

**关键**：所有开销都从 `density_func()` 这一个入口累加。看任何一个
云相关着色器，先数它调了几次 `density_func()`。

### 4.5.2 三个着色器各自的成本

#### ① 体积云 `shaders/anim/cloud-volume.gdshader`

```
MARCH_STEPS = 16（常量）
每个像素：
  光线步进      16 步 × density_func(40)      = 640 hash
  步进后着色     2 × fbm(40)                   =  80 hash
  空区域探测     3 × density_func(40)          = 120 hash  ← 见下方说明
  ────────────────────────────────────────────
  合计                                         ≈ 840 hash/像素
```

**渲染方式**：一个 320×10×320 的 `BoxMesh`（**只有 12 个三角形**），
所以开销**完全在像素着色**，与几何量无关。这也解释了为什么
"关掉体积云"能大幅提速，但 `primitives` 计数几乎不变。

#### ② 云影层（地面投影）`shaders/anim/cloud-shadow.gdshader`

```
每个像素：4 步 × density_func(40) = 160 hash
```
覆盖 180×180 的地面平面。

#### ③ 地形云影 `shaders/terrain/height-blend.gdshader`

**这是最容易被忽略的一处**：地形着色器**内联了自己的一份云噪声**
（`hash`/`noise`/`fbm_clouds`/`density_func`/`cloud_shade` 全都有），
与场景里的 `CloudLayer3D` 是**两套完全独立的开销**。

> ⚠️ 所以"关掉体积云，地形仍然很贵"是**正常的**——地形里那份云影计算照旧在跑。
> 我们一度以为关云没生效，实际是这个原因。

地形每像素还有 **8 次纹理采样**（草/土/岩/雪的 albedo + height）
做 height-blend 混合。

### 4.5.3 四项优化（按收益排序）

#### 优化 1：`fract(sin(n)*k)` → 整数 hash ✅ 收益最大

```glsl
// 原（GPU 上 sin 是多周期超越函数，而这里每像素要跑上千次）
float hash(float n) { return fract(sin(n) * 753.5453123); }

// 现（整数位运算吞吐远高于 sin）
float hash(float n) {
    uint x = uint(int(n));
    x ^= x >> 16u;  x *= 0x7feb352du;
    x ^= x >> 15u;  x *= 0x846ca68bu;
    x ^= x >> 16u;
    return float(x & 0x00ffffffu) / float(0x01000000u);
}
```

⚠️ **Godot 的 `>>` 要求两边同类型**，右操作数必须写 `16u` 而不是 `16`，
否则报 `Invalid arguments to operator '>>': 'uint, int'`（我们踩过）。

**视觉等价性**（已用数值验证）：整数 hash 的分布质量不比 sin-hash 差——

| | 均值 | 标准差 |
| --- | --- | --- |
| sin-hash | 0.5005 | 0.2840 |
| **整数 hash** | 0.4995 | **0.2889** |
| 理想均匀分布 | 0.5 | 0.2887 |

噪声插值结构与 8 个角点索引均未改动。

#### 优化 2：地形云影**只算一次** ✅

原来 `cloud_shade()` 被调用了两次，算的是**完全相同**的值：

```glsl
void fragment() { float cs = cloud_shade(world_pos);  /* 第 1 次 */ }
void light()    { float cs = cloud_shade(world_pos);  /* 第 2 次，重复！ */ }
```

改为用 `varying float cloud_shade_cached` 在 `fragment()` 里算好、
传给 `light()` 复用（Godot 先跑 `fragment` 再跑 `light`）：

```
320 hash → 160 hash（省一半）
```

#### 优化 3：地面云影竖直采样 4 → 2 步 ✅

```glsl
const int CLOUD_SHADOW_STEPS = 2;   // 原为 4，想恢复层次改回 4 即可
...
optical *= 4.0 / float(CLOUD_SHADOW_STEPS);  // 按比例归一，保持整体明暗不变
```

**依据**：地面云影的本质是"某点正上方的柱状光学厚度"，玩家看得见的是它的
**横向**变化（随时间漂移的云块）。纵向 4 个采样算的是同一团云在不同高度的
密度，高度相关，属**过采样**。这是视觉无损的取舍，不是降级。

```
160 hash → 80 hash（省一半）
```

#### 优化 4：空区域提前退出 ⚠️ 有前提

```glsl
// 先做 3 个粗采样探测，无云直接 discard
float probe = 0.0;
for (int k = 0; k < 3; k++) { ... probe += density_func(pp, TIME); }
if (probe * march_step < 0.0015) { discard; }
```

**它的成本是 +120 hash/像素**（3 次 `density_func`），只有当
**屏幕上大部分像素是空的**（大片天空）时才划算。如果画面上云很多，
这是**净亏损**。

> 若要调优，这个常量 `0.0015` 是阈值：调高 = 更多像素被判定为空、
> 更激进地跳过（但可能漏掉稀薄云）。

#### 优化 5（顺手）：水面微扰降级

```glsl
// 原：3D noise（8 次 hash），但这里只是个低频色斑
vec3 water = ... * (0.88 + 0.12 * noise(world_pos * 2.4));
// 现：单次 hash
vec3 water = ... * (0.88 + 0.12 * hash(floor(world_pos.x*2.4) + floor(world_pos.z*2.4)*157.0));
```

**着色器优化的累计收益**（同一场景，逐步测量）：

| 阶段 | FPS | 倍数 |
| --- | --- | --- |
| 起点（原始代码） | 39 | 1.00× |
| + 体积云整数 hash + 提前退出 | 73 | 1.87× |
| + 地形云影去重 + 整数 hash | **116** | **2.97×** |

**A/B 隔离**（同机连续测量，1280×720）：

| 配置 | FPS | primitives |
| --- | --- | --- |
| 关地形 | 80 | 345,968 |
| 关云 | 80 | 618,564 |
| **全开** | **71** | 629,062 |

→ 地形与云**各占约 9 FPS（合计约 12%）**。

⚠️ 注意：上表的 39→116 是在**显示器 60Hz、窗口模式**下测的；
后期某轮测到 30 FPS 是显示器被设成 30Hz 所致（见第 1 节），
与着色器无关。

### 4.5.5 如果还要继续优化

按收益预期排序：

1. **降低 `MARCH_STEPS`**（16 → 8）：直接砍一半步进成本，代价是云的
   层次/厚度感变差。这是最直接的一刀。
2. **把「提前退出」阈值调高**：让更多天空像素走 discard 路径
   （先量一下画面上云的占比决定是否值得）。
3. **云影层与地形云影合并**：两者算的是同一团云，目前是两套独立开销。
   可以只保留一份、用 `varying`/uniform 传递——但需要处理两者的采样
   坐标系差异（一个是世界 XZ，一个是地形 UV）。
4. **用整数 hash 进一步简化**：当前用了 2 轮乘-异或混合（质量优先），
   可减到 1 轮（质量略降、速度更快）。
5. **`#include` 收敛源码**：目前 4 个着色器各有一份噪声拷贝。
   `ShaderInclude` 只改善**可维护性**（改一处生效四处），
   **不减少运行时开销**（GPU 没有共享库概念，编译后仍是各一份机器码）。

## 5. GC：先量清楚再下结论

日志里的 `gcGen0/1/2`（累计次数）与 `gcPauseMs`（累计暂停）由
`PerfMonitor` 采集。**用相邻样本求增量**才有意义。

> **我们犯过的错**：曾用"GC 暂停 10.8ms/秒"判断 GC 是卡顿主因——
> 但那是拿**每秒**的量去比**单帧**预算。正确算法是：
>
> ```
> GC 暂停总时长 ÷ 总帧数 = 每帧 GC 成本
> 实测：1460ms ÷ 9867 帧 = 0.148 ms/帧，占 14.5ms 预算的 1%
> ```
>
> 结论：**GC 不是主因**。Gen0 频率高（~12 次/秒）不等于卡顿——
> Gen0 回收本身廉价（晋升缓冲区）。

已做的分配优化：
- `EntityLayer3D.SyncEntities` 去掉每帧 `_nodes.Keys.ToArray()`
- `EntityView.Get` 增加解析缓存（此前每次调用都 `ParseFrom`）

## 9. 移动卡顿：渲染帧率之外的第二种"卡"

上面第 1~8 节讲的是**帧率**问题（显示器/着色器/GC）。但"卡好跳的感觉"
还有第二种来源：**帧率正常，位置更新却不连续**。

### 9.1 症状特征

- FPS 稳定在 60/70，帧节拍没有尖峰（`FrameSpikeRatio` 接近 0）
- 但**移动中的实体**看上去一跳一跳，或"走两步顿一下"
- 自己（本地预测）反而比别的实体顺——因为自己不走插值缓冲

### 9.2 根因：服务端只在跨格时下发位置（已修复）

客户端 `PositionSmoother` 的设计前提是"服务端每 tick 广播连续子格偏移
（Position + Sub）"，但服务端 `MoveSystem` 提交阶段只判 `ApplyDisplacement`
的返回值（= 是否跨格），于是**移动中但不跨格的 tick 不下发 `Moveable`**：

```
10 格/秒 ÷ 20Hz = 0.5 格/tick  →  每两个 tick 才跨一格
→ 客户端只拿到约 10Hz 的有效位置更新，而渲染是 60FPS
```

实测证据（修复前）：

| 指标 | 数值 |
| --- | --- |
| 玩家 `MoveableTick` 下发 | 同值 436 / 变值 378 |
| `PositionSmoother` 样本数 | 长期只有 1 个样本（`单样本×12921`） |
| 渲染帧位置不变 | 88/143 = **61%** |

这是典型的**契约与实现脱节**：注释按"每 tick 下发"写，实现从未做到。

### 9.3 修复 A（服务端）

提交阶段在 `ApplyDisplacement` 前后对比 Sub，只要连续位置
（`Position + Sub`）变了就标脏 `Moveable`；`Position` 仍只在跨格时标脏
（避免无谓的全量字段下发）；停止的实体不标脏，不增加流量。

验证：`go run ./tools/snapprobe -uid 45 -duration 8s -v`

```
64.5 → 65.0 → 65.5 → 66.0 → 66.5 → 67.0 …   （每帧 +0.5 格，无重复）
第 1 秒位置变化 20 次，正好等于 tick 率
```

⚠️ 排查时**不要**只看到"位置不变"就断定下发有缺口：
`Position` 只在跨格时下发是有意设计，连续位置要用
`最近整格 + Moveable.SubX` 算。若 `subX` 长期钉在 `0.999` 且不变，
那是**实体撞墙卡住**（合法停止），不是 bug。

### 9.4 修复 B（客户端外推 + 平滑过渡）

插值只能补帧，补不了**样本迟到**：某个 tick 的快照晚到/丢失时，
纯插值会"卡住等下一帧"。因此 `PositionSmoother` 增加三层处理：

1. **延迟插值**：固定 `delayTicks` 后相邻样本线性插值（原有能力）
2. **速度外推**：样本用尽时按速度继续前进。速度**优先取服务端权威
   `Moveable.VelX/VelY`**（已含坡度与避让结果，比"末段位移"准）；
   服务端确认停止（速度清零）时立即停止外推，避免停下后滑行
3. **残差平滑吸收**：外推期间到达的样本若与预测不符（残差 >
   `blendThreshold`），**不瞬移**——把"当前显示位置"记为混合起点，
   在 `blendTicks` 内过渡到权威轨迹

### 9.5 实现这条逻辑时踩到的三个坑

这三个都是**单元测试/变异测试**逼出来的，不是靠看代码发现的：

| 坑 | 错误写法 | 后果 |
| --- | --- | --- |
| 外推收尾倒退 | `vx * beyond * decay` | `beyond` 增长而 `decay` 下降，乘积**先增后减** → 画面倒退 0.79 格（橡皮筋）。正解：`MathF.Min(beyond, maxExtrapTicks)` 钳住端点 |
| 混合方式过冲 | 给基础轨迹**叠加残差偏移** | 与"基础轨迹自身仍在向新样本插值"叠加 → 先过冲再回摆，且**最终停在错误位置**（收敛到 10.912 而非权威 10.112）。正解：起点→权威轨迹的空间混合，按定义必然收敛 |
| 采样函数有副作用 | `SampleAt()` 内部改 `Extrapolating`/混合状态 | 状态被"查询"污染，残差判据失效（`blendDist` 恒为 0）。正解：采样保持纯函数，状态由 `Current()` 统一维护 |

**教训**：位置平滑这类"带时间维度的状态机"，光看代码很难判断对不对；
写一组断言"逐帧位移连续、不后退、最终收敛"的测试，再跑**变异测试**
（故意改坏一行，看测试是否报警）才靠得住。本次 9 个变异体里 6 个被测试捕获，
剩下 3 个经证明是**等价变异体**（对应防线在结构上不可达），不是测试缺口。

### 9.6 在线健康度指标

`PerfMonitor` 每秒打印一次：

```
SMOOTH 外推帧=<n>/<total> (<pct>%)
```

外推帧 = 该帧没有可用样本、只能按速度推测的帧数。修复后应接近 0；
持续偏高说明服务端下发有缺口或客户端渲染落后（掉帧）。

## 10. 排查顺序（补：移动卡顿版）

沿用第 0 节的思路，但移动卡顿要**先确认位置数据本身连不连续**：

1. 先看 FPS 是否真的够（第 1 节：显示器刷新率）
2. 帧率正常但移动跳 → 看 `SMOOTH 外推帧` 占比
3. 占比高 → 查服务端是否每 tick 下发（`snapprobe`）
4. 占比低但仍跳 → 查插值器本身的逐帧位移序列（用 `SmoothProbe` 式测试）
5. **还是跳 → 看服务端 tick 的量级**（第 11 节：float 精度）

## 11. 移动卡顿的真凶：插值时钟用了 float（tick 一变大就量化）

> 这一节是 2026-09 那次"玩家和生物移动很卡、但 FPS 一直很高"的根因。

### 11.1 症状

- 帧率很高（100+），帧节拍没有尖峰，`SMOOTH 外推帧` 接近 0
- 但移动**一顿一顿**，尤其是**其他玩家 / 生物**（自己走本地预测，不走插值）
- 不是一直这么卡：**服务端跑得越久越明显**（存档里的 tick 一直在涨）
- 与帧率无关甚至**帧率越高越明显**

### 11.2 根因

`PositionSmoother` 把虚拟插值时钟写成 float：

```csharp
// 错：tick 是服务端累计 tick（存档会把它带到几十万/上百万）
var dt = _latestTick + sinceUpdate / 50f - _delayTicks;
```

float 只有 **24 bit 有效位**，`dt` 的量级就是 tick 本身，于是它的最小步长（ULP）随 tick 变大：

| 服务端 tick | float ULP | 折合时间 | 对逐帧位移的影响（10 格/秒） |
| --- | --- | --- | --- |
| 0 | ~1e-7 | ~0 | 无 |
| 5e5 | 0.03125 | 1.56 ms | 0.016 格台阶 |
| **7.2e5（≈10 小时）** | **0.0625** | **3.125 ms** | **0.031 格台阶** |
| 1.1e6 | 0.125 | 6.25 ms | 0.063 格台阶 |
| 2.2e6 | 0.25 | 12.5 ms | 0.125 格台阶 |

**为什么"帧率越高越明显"**：120FPS 每帧只推进 `8.33ms/50ms = 0.167 tick`，
而台阶是 0.0625 tick —— 台阶占了单帧的 **37.5%**；60FPS 每帧 0.333 tick，只占 18.8%。

**为什么"跑久了才卡"**：tick 从存档恢复并持续累加，ULP 每翻一倍就跳一档。
到 2.2e6（约 30 小时）时台阶 (0.25 tick) 已经**大于单帧推进量 (0.167 tick)**，
虚拟时钟会**隔帧才动一次**——角色一帧不动、下一帧走两步，肉眼就是"一卡一跳"。

### 11.3 证据（怎么当场认出来）

给插值器加一个 `LastVirtualTick` 诊断口，逐帧打印，会看到值是 **1/16 的整数倍**
（= ULP 0.0625）：`719891.6875, 719892.0, 719892.3125, 719892.6875 …`

而正确实现下 `dt` 的增量应是**平滑的 frameMs/50**（60FPS 约 +0.333/帧）。
本手册配套的 `MoveTrace`（见 11.6）会输出 `e<id>_dt` 列，直接看这一列即可。

离线复现/回归见 `Starve.Core.Tests/TickPrecisionProbeTests.cs`：

```
# 修复前（float）
fps=60  tickBase=719892  sd=0.02365  ratio=1.236
fps=120 tickBase=100000  sd=0.01181  ratio=1.137
# 修复后（double）：所有 tickBase 的 sd 与 tick=0 完全一致（ratio=1.000）
```

### 11.4 修复

虚拟时钟整条链路改 `double`：`SampleAt` 的 `dt`、`Evaluate(targetTick)`、
`beyond`/`clamp` 全部按 double 算（位置本身仍是 float，量级只有几百格，无精度问题）。

> **教训**：**时间轴上的"绝对计数"永远不要用 float**（tick、帧号、序列号、
> 文件偏移……）。float 的精度是**相对**的，绝对计数只会越来越大。
> 这类 bug 有个恶劣特性：**开发时（tick 小）复现不出来，上线跑几小时才出现**。

### 11.5 顺手修掉的一个演示模式 bug

`STARVE_DEMO_MOVE`（截图/演示用自动行走）只调了 `SetIntent`，**没有置
`_ownIntentMoving`**。而 `ApplyWorld` 里有一段"服务端没有 Path 时把本地意图清成 (0,0)"
的兜底逻辑，会每 20Hz 把演示模式的意图抹掉 → 本地预测走走停停。
真实按键输入走 `MoveController.OnIntent`，会正确置位，所以**只影响演示模式**。
已在演示分支补上该标志。

### 11.6 工具：逐帧移动追踪 `MoveTrace`

```bash
# 对着本地 gate 自动行走 9 秒，把每帧的"预测 vs 权威 vs 和解"落成 csv
STARVE_MOVE_TRACE=1 STARVE_DEMO_MOVE=-1,0 STARVE_MOVE_TRACE_MS=9000 \
  STARVE_MOVE_TRACE_OUT=/tmp/move.csv make run
```

一行一帧，列分四段（`STARVE_MOVE_TRACE_N` 控制末尾额外追踪几个动态实体，默认 2）：

| 段 | 列 | 用途 |
| --- | --- | --- |
| 头 | `frame,tMs,deltaMs,snap` | `snap=1` 表示这帧应用了新快照 |
| 输入 | `canPredict,ticked,pending,acked` | 本地预测是否在跑、命令确认有没有积压 |
| 本地预测 | `locX,locY,locVX,locVY,locSpeed,locDirX,locDirY,locSlope` | 逐帧实测的预测速度 + 当前坡度因子 |
| 渲染 | `rendX,rendY,rendZ,dRendY,tileH` | 真正画出去的位置；**`dRendY` 是"上下卡"的直接指标** |
| 服务端 | `srvX,srvY,srvVelX,srvVelY,srvVelSpeed,srvEffSpeed,srvDirX,srvDirY,srvPath,srvStopped,srvStepX,srvStepY,srvStepSpeed,stepTicks` | 权威位置 + **声明的**速度与行为 + **实际**这一步走了多少 |
| 和解 | `errX,errY,err,impliedLeadMs,driftX,driftY,driftSpeed,decision,k,soft,hard,stopSettled` | 做了什么决定、误差多大、折算成多少毫秒领先 |

**怎么读（重要）**：

- **"本地现在" vs "服务端过去"天然差一个网络领先量**（≈ v×往返延迟），那不是失配。
  真正判据是 `drift*`：**同一 tick 跨度内**本地预测走了多少 vs 服务端走了多少
  （它把校正排除在外，是"纯预测"位移）。直线行走应为 0。
- `srvStepSpeed`（实际位移）与 `srvVelSpeed`（声明速度）不一致 → 权威速度字段在撒谎
  （贴岸/被挡时会，见 P1.5 的 P4）。
- `dt`（被追踪实体）的逐帧增量应平滑，出现台阶/回退就是插值时钟的问题。
- `impliedLeadMs` 把 `err` 折算成领先毫秒数：它应该≈网络单程延迟且**稳定**；
  逐步变大说明预测在持续偏离。

### 11.7 后续：预测/和解重构

顿挫在 float 修复后**没有完全消失**（长走之后偶发、上下更明显）。原因与重构方案见
`P1.5-PREDICTION-REPLAY.md`：核心是"拿本地现在比服务端过去"会稳定触发 20Hz 回拉，
以及"停止=一次到位吸附"会在松键时硬跳一次（角色站在高度场上 → 上下跳）。

### 11.8 这次排查中**排除**的假设（留档，别再走一遍）

| 假设 | 怎么排除的 |
| --- | --- |
| 服务端没每 tick 下发 | `snapprobe`：20 样本/秒，每次 +0.5 格，`不变占比 0%` |
| 下发成簇 / 网络抖动 | 自写到达时刻探针：间隔 p50=50.1ms、min 47.8、max 51.5，**0 次 2ms 内成簇** |
| 客户端掉帧 / GC | 帧中位 8.33ms、尖峰占比 0.16%、GC 0.06ms/帧 |
| 相机滤波造成屏幕上抖 | 把 `sx = worldX - camX` 分离出来看：稳态下两者逐帧增量都精确等于 0.1667 |
| 自己走的是插值 | 自己的位置走 `OwnMovementSim` 本地预测，稳态逐帧位移**精确** 0.1667 格 |
| 占位物视觉钉点 `BlockVisual.Center` 量化 | 它只是 `pos + 宽高/2` 的常量偏移，不减帧 |
| 坡度速度公式与服务端不一致 | 客户端已用 `LogicalHeightAt`（崖壁带）对齐服务端 `worldmap.HeightAt` |

### 11.9 重构后的对抗测试：网络层的"偶发卡"怎么查（2026-02）

顿挫的**第二类**根因在预测/和解组件里，与 fps 无关，特征是"长时间走后偶发一下"。
现在有一整套**不启动 Godot** 的测试专门打这些情况，排查时先看它们是否全绿：

```bash
dotnet test Starve.Netcode.Tests --filter "FullyQualifiedName~DelayedReplayRollbackTests"
dotnet test Starve.Core.Tests    --filter "FullyQualifiedName~NetcodeAdversarialLinkTests"
```

边界口径与每条修复的原因记在 `client-pre-pic.md` §12（含修复前后的"直接贴"占比表）。
排查真实链路时对着 `MoveTrace` 的 `decision`/`err` 看：

- `decision=Snapped` 频繁 → 真失配大（撞墙/传送/两端世界真相不一致），看 `srvStepSpeed`；
- `decision=Blended` 但屏幕上"拖影"很久 → 累积残差太大，看过渡时长是否被 `err` 而不是残差顶着；
- `replayClamped=1` 长期为真 → 延迟超出 `MaxReplayTicks`（1 秒），客户端会稳定落后；
- 换向那一下 `err` 恒为 ~1 格 → **已知问题**：输入的生效 tick 是在发送时刻冻结的，
  抖动下会差 1~3 tick；根治要服务端回传"最后一条输入在哪一 tick 生效"（见 §9 第 3 条）。
- 开局 1~4 秒内换向 `err` 偏大 → 爬升期（生效延迟估计限速逼近），属于已量化、已知的启动代价。
