# 客户端性能排查手册

> 本文记录"客户端卡顿"的排查路径与实测基线。**先按本文的顺序排除环境因素，
> 再怀疑代码**——我们曾花了很多轮去优化着色器和 GC，最后发现根因是
> **显示器被设成了 30Hz**。

## 0. 排查顺序（重要）

按以下顺序，**从外到内**。前面的没排除掉，后面的结论都可能是噪声。

| 顺序 | 检查项 | 怎么查 | 典型症状 |
| --- | --- | --- | --- |
| 1 | **显示器刷新率** | 系统设置 → 显示器 → 刷新率 | 帧率精确锁在刷新率或其 1/2 |
| 2 | 窗口是否在前台 | 点一下游戏窗口 | 后台窗口被 macOS 节流 |
| 3 | 其他进程抢资源 | `ps aux \| sort -rk3 \| head` | CPU 被打满 |
| 4 | 启动阶段 vs 稳态 | 看 F3 面板随时间变化 | 前 5~30 秒低、之后恢复 |
| 5 | GPU 子系统 | F3 面板的地形/云/植被开关 | 关掉某项明显提速 |
| 6 | 才轮到代码 | 本文下面的章节 | —— |

## 1. 显示器刷新率：最容易误判的一项（我们踩过）

### 症状特征

```
FPS 精确 = 30（或 60 / 120，即刷新率或其整数分之一）
frameMs 精确 = 33.33（= 1000/30，不是 33.5 或 34）
processMs ≈ frameMs   ← 但下面这条是关键
CPU 只有 3%
```

**`processMs` 很高但 CPU 很低 → 在等显示器，不是在算。**

### 怎么确认

```bash
system_profiler SPDisplaysDataType | grep -E "Resolution|UI Looks like|Main Display"
```

输出会形如：

```
HP D27k:
  Resolution: 3840 x 2160 (4K)
  UI Looks like: 1920 x 1080 @ 30.00Hz     ← 就是这里
  Main Display: Yes
```

### 注意

- **`--disable-vsync` 通常无效**：macOS 全屏下 Metal 仍按显示器刷新率提交。
  所以"关了 vsync 还是 30"**不能**排除刷新率问题（我们一度据此误判）。
- 4K 分辨率跑 30Hz 常见于**带宽不足**：HDMI 1.4 / 劣质线 / Type-C 转 HDMI
  转接头。换 **DisplayPort** 或降分辨率通常可恢复 60Hz。
- 多显示器时窗口在哪个屏，受哪个屏的刷新率约束。

## 2. 启动阶段：自定义着色器编译

### 症状

启动后前 **5~30 秒**帧率被锁在 30，之后自动恢复。期间 Godot 进程 CPU 打满。

### 原因

**Godot 的自定义着色器不进磁盘缓存。** 检查缓存目录会发现里面
全是引擎内置管线：

```bash
ls ~/Library/Application\ Support/Godot/app_userdata/<项目名>/shader_cache/
# SceneForwardClusteredShaderRD / SSAO / TAA / Fsr ... 唯独没有 res:// 下的 .gdshader
```

所以每次启动都要从源码重新编译我们那 8 个着色器。

### 已做的缓解

`GameRoot.WarmUpShaders()` 在启动时把着色器挂到离屏节点上强制编译，
把这段卡顿**前移到进入游戏之前**。实测 30FPS 期从 5~28 秒缩短到 3~4 秒。

注：这是**把卡顿前移，不是消除**——编译总量不变，且仍有 3~4 秒残留
（那部分是纹理/资源加载）。彻底消除需要预编译管线缓存，Godot 当前不提供。

## 3. 帧节拍（frame pacing）：平均 FPS 会骗人

**平均帧率正常不代表不卡。** 帧时间忽长忽短在视觉上就是"一顿一顿的"。

F3 面板的"帧节拍"行、以及日志里的 `frameMedianMs` / `frameP95Ms` /
`frameWorstMs` / `frameSpikeRatio` 专用于此。

实现见 `Starve.Core/FrameTimeStats.cs`（纯逻辑，可单测）。

> **坑**：`JitterRatio` 用**最坏帧**/中位数，不能用 P99/中位数。
> 偶发单帧尖峰（121 帧里 1 帧）在 P99 上取不到，比值会是 1、看不出问题。

## 4. 渲染子系统：A/B 隔离

F3 面板有地形/体积云/植被/Glow 开关，可逐个关闭做 A/B。

实测（Apple M4 Pro，1280×720，同一场景连续测量）：

| 配置 | FPS | 图元 |
| --- | --- | --- |
| 关地形 | 80 | 345,968 |
| 关云 | 80 | 618,564 |
| **全开** | **71** | 629,062 |

→ 地形与云**各占约 9 FPS（合计约 12%）**。

### 已做的着色器优化

1. **`fract(sin(n)*k)` → 整数 hash**：云/地形的噪声每像素调用上千次，
   `sin` 是 GPU 上的多周期超越函数。
2. **云影只算一次**：`cloud_shade()` 原先在 `fragment()` 与 `light()` 里
   各调一次、算的是同一个值。
3. **地面云影竖直采样 4 → 2 步**：云影的可见信息是**横向**漂移，
   纵向 4 个采样高度相关，属过采样。

> ⚠️ 注意：**地形着色器内联了自己的一份云噪声**，与场景里的
> `CloudLayer3D` 是两套独立开销。所以"关掉体积云，地形仍然很贵"是正常的。

## 5. GC：先量清楚再下结论

日志里的 `gcGen0/1/2`（累计次数）与 `gcPauseMs`（累计暂停）由
`PerfMonitor` 采集。**用相邻样本求增量**才有意义。

> **我们犯过的错**：曾用"GC 暂停 10.8ms/秒"判断 GC 是卡顿主因——
> 但那是拿**每秒**的量去比**单帧**预算。正确算法是：
>
> ```
> GC 暂停总时长 ÷ 总帧数 = 每帧 GC 成本
> 实测：1460ms ÷ 9867 帧 = 0.148 ms/帧，占 14.5ms 预算的 1%
> ```
>
> 结论：**GC 不是主因**。Gen0 频率高（~12 次/秒）不等于卡顿——
> Gen0 回收本身廉价（晋升缓冲区）。

已做的分配优化：
- `EntityLayer3D.SyncEntities` 去掉每帧 `_nodes.Keys.ToArray()`
- `EntityView.Get` 增加解析缓存（此前每次调用都 `ParseFrom`）

## 6. 实测基线（供回归对比）

Apple M4 Pro / 1280×720 / 窗口模式 / 显示器 60Hz / 全特效开启：

```
FPS            71 ~ 76
帧中位         13.9 ms
帧 P95         15.3 ms
尖峰占比       0%（稳态；启动前 10 秒除外）
CPU            3 ~ 20%（看场景）
drawCalls      ~365
primitives     ~62 万
textureMem     ~350 MB
videoMem       ~950 MB
```

**若实测明显偏离此表，先回到第 0 节的排查顺序。**

## 7. 工具

- **F3 面板**：实时 FPS、帧节拍、显存、地形/云/植被/Glow 开关
- **性能网页**：<http://127.0.0.1:18765/>（端口被占则顺延到 18766…）

    `/api/logs` 日志文件列表

  （每秒一行，含帧节拍与 GC 计数）

## 8. 一次真实的排查记录（复盘）

| 轮次 | 怀疑对象 | 结论 |
| --- | --- | --- |
| 1 | 服务端 | ❌ 排除：99% 的 tick < 1ms |
| 2 | 客户端预测被回拉 | ❌ 排除：maxErr 0.167 格、soft=0、hard=0 |
| 3 | `hdr_2d` / Glow | ❌ 排除：关掉无变化 |
| 4 | 体积云着色器 | ✅ 真问题：39 → 73 FPS |
| 5 | 地形着色器 | ✅ 真问题：73 → 116 FPS |
| 6 | GC | ⚠️ 算错了，实际只占 1% |
| 7 | 启动着色器编译 | ✅ 真问题：前 28 秒锁 30 FPS |
| 8 | **显示器刷新率** | 🎯 **真正的根因**：显示器是 30Hz |

**教训**：前 7 轮找到的都是真实优化（确实提升了帧率），但**都不是**
用户当时感受到的"卡"。如果第 0 步先查显示器，可以直接定位。

**先问"帧率精确锁在多少"，再看别的。**
